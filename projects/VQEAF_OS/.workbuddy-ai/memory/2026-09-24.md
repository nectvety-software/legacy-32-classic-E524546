# 2026-09-24 — VQEAF OS: first real PlatformIO build + flash to hardware

## What was asked
`nạp vào thiết bị` — flash VQEAF OS v2.3.4 onto the physical ESP32-S3.

## Outcome: done and verified

Built and flashed **v2.3.4** to the board on **COM3** (CH340 USB-UART).

- `firmware.bin` = 1,473,136 bytes (22.48 % of the 6.25 MiB app slot)
- `firmware.elf` = 25,828,048 bytes
- esptool: `Chip is ESP32-S3 (revision v0.2)`, `MAC: fc:01:2c:cc:eb:6c`
- Wrote bootloader `0x00000000`, partitions `0x00008000`, boot_app0 `0x0000e000`,
  app `0x00010000`; `Hash of data verified.`; `Hard resetting via RTS pin...`
- Boot capture on COM3: ROM banner `rst:0x1 (POWERON), boot:0x8
  (SPI_FAST_FLASH_BOOT)`, then core logs to 518 ms, **no panic in 20 s**.

This is the **first successful PlatformIO target build** of this project.
v2.3.3 and v2.3.4 both shipped with `platformio_target: BLOCKED`.

## Two real bugs found and fixed

### 1. LDF could not resolve `SD_MMC -> FS`

`SD_MMC.h:21:10: fatal error: FS.h: No such file or directory`

Root cause: `SD_MMC.h` puts `#include "FS.h"` inside
`#ifdef SOC_SDMMC_HOST_SUPPORTED`, and the whole of `SD_MMC.cpp` (lines 18-211) is
wrapped in the same guard. That macro is defined in `soc/soc_caps.h` — a *header*
the LDF preprocessor does not expand. So the LDF saw zero includes for SD_MMC,
created no dependency edge, and never added `libraries/FS/src` to its include path.

Proved it by diffing the actual `-I` flags (`pio run -v`): `LittleFS.cpp` got
`-Ilibraries/FS/src`, `SD_MMC.cpp` did not.

Fix applied to `platformio.ini` (documented inline):
```ini
-D SOC_SDMMC_HOST_SUPPORTED=1
```
Token-identical redefinition to `soc_caps.h`, so the real compile is unaffected.
`lib_ldf_mode = deep+` / `lib_compat_mode = strict` left untouched on purpose.

### 2. False `[SUCCESS]` with no `firmware.bin`

After editing `build_flags`, PlatformIO tried to wipe `.pio/build` and was
**blocked** (bulk-delete guard, 634 files):

```
Can not remove temporary directory `...\.pio\build`. Please remove it manually to avoid build issues
```

It continued against the stale `.sconsign311.dblite`, SCons found nothing to do,
and printed `[SUCCESS] Took 39.42 seconds` — with **zero** `Compiling` lines and
no `firmware.bin`.

Fix: `rm -rf .pio/build` (keep `.pio/libdeps`), then rebuild. Real build = 310
`Compiling`/`Archiving` lines + `Linking ... firmware.elf`, 293 s.

**Rule: never trust `[SUCCESS]`. Check `firmware.bin` exists and the log has
`Compiling` lines.**

## Finding: app serial logs are NOT on the UART port

`ARDUINO_USB_MODE=1` + `ARDUINO_USB_CDC_ON_BOOT=1` (both in `platformio.ini`) make
`Serial` the **native USB CDC** (GPIO19/20), not UART0:

- `cores/esp32/HWCDC.h:112` -> `extern HWCDC Serial;`
- `cores/esp32/HardwareSerial.h:330` -> `extern HardwareSerial Serial0;`

`src/main.cpp` logs everything through `Serial`, so `[VQEAF][BUILD]`,
`[VQEAF][MEM]`, `SD: mounted`, `[S3DIAG][BOOT]` never reach COM3/CH340.

This contradicts the project's own docs:
- `docs/BOARD_BUILD_V233.md` §5 — "Connect USB/serial at 115200 ... Verify
  `[VQEAF][BUILD]`, `[VQEAF][MEM]`"
- `docs/BOARD_TEST_V22_VN.md` §2 — `pio device monitor -b 115200`

Only true if the **native USB** port is connected. UART0 still shows the ROM
banner, core `ESP_LOGx` output and panic dumps, so it remains a valid crash
detector. Not changed — flag it to the user, don't silently rewrite the USB config.

## Still unverified
The 240x320 ST7789 UI itself. Nothing on COM3 can prove the display rendered;
that needs eyes on the screen (or the native USB port connected).

## Files touched
- `platformio.ini` — added `-D SOC_SDMMC_HOST_SUPPORTED=1` with an explanatory comment
- `.pio/build/` — regenerated (was stale/inconsistent)

## Reusable knowledge
Saved as skill `platformio-esp32-build-flash-verify`.

# 2026-09-24 (later) — packaged the build into flashable .img files

## What was asked
`đóng gói thành tệp .img` — package the firmware as an .img.

## What was produced

New script `tools/make_flash_image.py` (project is script-driven, so this is
repeatable rather than a one-off command). It reads the build output, merges the
four regions with `esptool merge_bin`, and **verifies its own output**.

Outputs in `dist/`:
- `vqeaf_os_v2.3.4_merged.img` — 1,538,672 B. Sparse; flash at `0x0`.
  sha256 `5a96b902f54e5bcd4984e8d74feaa397e072cb148ea4daf8b7f101b9c48c83af`
- `vqeaf_os_v2.3.4_16mb.img` — 16,777,216 B. Same content, `0xFF`-padded.
  sha256 `e6b75b38d3a5a026374ec41ab788ec4f07c09ba06d276e69dbc1a60f4d615119`

Layout used (taken from the `pio run -t upload` log, not guessed):
`0x0` bootloader, `0x8000` partitions, `0xE000` boot_app0, `0x10000` app.
`boot_app0.bin` comes from `framework-arduinoespressif32/tools/partitions/`.

## Verification done
- All four regions byte-compared against the source files with `head`/`tail` +
  `cmp` — independent of the Python script that produced them. All IDENTICAL.
- Magic bytes: `e9` at `0x0`, `aa 50` at `0x8000`, `e9` at `0x10000`.
- `esptool image_info` on the merged image: checksum valid, validation hash
  valid, and **`Entry point: 403c98d0` matches the ROM banner `entry 0x403c98d0`**
  from the board already flashed — so the image really is that firmware.
- 16 MB variant is `0xFF` beyond the app.

## Important caveat (told the user)
A "flash at 0x0" image `0xFF`-fills the gaps between regions, and on this layout
**NVS (`0x9000`) sits in a gap** — so flashing the merged image erases saved
settings. Normal for a factory image, but worth stating. NVS is currently
near-empty anyway (fresh).

## Files touched
- `tools/make_flash_image.py` — new
- `dist/vqeaf_os_v2.3.4_merged.img`, `dist/vqeaf_os_v2.3.4_16mb.img` — new
- skill `platformio-esp32-build-flash-verify` — added a packaging section

filtered out of any log that goes into documentation.

## Windows portability: 3 real bugs in the host test harness
`tools/verify_v240.py` was 4/7 FAIL here. Not code regressions — the harness
assumed a POSIX host. All three fixed (firmware untouched):
1. **`tools/qeapp_host/Arduino.h`: `FILE_READ "r"` / `FILE_WRITE "w"` were text
   mode.** On Windows that CRLF-translates and treats `0x1A` as EOF, corrupting
   every binary `.qeapp` read so `installer.inspect()` rejected the shipped
   signed sample. Linux `"r"` is already binary, so the bug is invisible there.
   -> `"rb"` / `"wb"`. **This was the interesting one.**
2. **POSIX two-argument `::mkdir(path, 0777)`** in `tools/qeapp_host/FS.h`,
   `test_installer.cpp`, and `tools/storage_host/{FS.h,test_atomic.cpp}`.
   MinGW declares one-argument `mkdir(const char*)` -> hard error under
   `-Werror`. Added shared `tools/host_mkdir.h`.
3. **Bare `python3`** in `test_v15_signature.py` / `test_v24_app_manager.py`
   (resolved to the managed Python 3.13, which lacks `cryptography`), plus a
   POSIX `st_mode & 0o077` permission assertion. -> `sys.executable`; skip the
   permission check on Windows.

Result: **7/7 PASS**. Needs `g++` at `/c/msys64/mingw64/bin/g++.exe` on PATH and
`mingw-w64-x86_64-openssl` (installed via pacman) for `-lcrypto`.

## Verification trap worth remembering
The ROM banner's `entry 0x403c98d0` is the **bootloader's** entry point, not the
app's. `image_info` on `firmware.bin` reports `40377588`; on `bootloader.bin` (or
on `merged.img`, which starts with the bootloader) it reports `403c98d0`. Compare
against the bootloader or you will wrongly conclude the flash is broken.

## SD oddity, reported honestly
First boot after flashing logged `sdmmc_init_ocr: send_op_cond (1) returned
0x107` (timeout). Five later boots were byte-identical and had **no** `sdmmc`
lines. Since `StorageService::begin()` always calls `SD_MMC.begin()`, absence of
the message means the mount succeeded — card settling, not a firmware fault.
Documented in the guide rather than quietly dropped.
